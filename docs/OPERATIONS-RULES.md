# 运维硬约束（OPERATIONS RULES）

> 这份文件是**血的教训**换来的。2026-10-19 夜间到 2026-10-20 凌晨，因为违反下面这些规则，
> 直接把用户的微信**消息库搞坏、聊天记录丢失**，并让客户端**反复崩溃**。
> **任何改动前先读这份。违反任何一条 = 事故。**

---

## R1. 绝不对微信客户端「强杀」

- ❌ `Stop-Process -Force` / `taskkill /F` 杀 `Weixin.exe` / `WeChatAppEx.exe`
- ✅ 只用 `CloseMainWindow()`，然后**等**它自己退出（可能 20~30 秒）
- 为什么：强杀会让 WCDB 的 WAL 停在半提交状态，微信下次启动会判定数据库不可信，
  把它**移进 `.factory` 隔离目录**、另建一个空库 → **用户看不到聊天记录**（实际发生过）。
- 例外：只有在「客户端已经无响应、且已等待 ≥60 秒」时才允许强杀，且必须**先备份 `db_storage`**。

## R2. 绝不「自动拉起客户端」

- 桥里那段 `检测到客户端已退出 → 自动重新拉起` 已改为**默认关闭**（`WECHAT_AUTOLAUNCH=1` 才开）。
- 为什么：它会在「用户正停在登录窗口」或「旧实例还没退干净」时**再 spawn 一个实例**，
  两个实例抢同一个数据目录 → 客户端崩溃 / 数据库损坏。
- **保持默认关闭。** 客户端退出就让人来启动。

## R3. 守护/看门狗只做「进程内自愈」

- 看门狗（`server.mjs` 里每 5 分钟）**只允许**：
  1. 语音发送运行时开关丢了 → 重新 `POST /Debug/VoiceSend {"on":true}`
  2. 轮询连续失败/暂停 → `poller.init()` 重新初始化
  3. 打日志
- **绝不允许**：重启客户端、重启桥、杀进程、spawn 任何东西。
- 客户端/桥的重启**必须由人**决定。

## R4. 换 DLL / 改 hook 的固定流程

1. 备份当前 DLL 到 `archive/version.dll.GOOD-<md5前8位>-<时间戳>`
2. 停桥（否则看门狗会去拉客户端）
3. **CloseMainWindow** 关客户端（R1），等 20~30 秒
4. 复制新 DLL
5. 启动客户端（带 `StartPort/RecvType/CallBackURL` 参数，工作目录=客户端目录）
6. **等**：轮询 `/QueryDB/debug` 直到 `dbs > 5` 且 `Weixin` 进程 ≥ 3（**别按时间判断**）
7. 起桥 → 验证收发
- **一晚最多做 2 轮。** 连做 3 轮以上必然出事（实际发生过：一晚上 10+ 次）。

## R5. 一次只改一件事，改完立刻验证，不合就回滚

- 不要「顺手把几个改动一起上」。一个改动 → 一个验证 → 再下一个。
- 验证不通过 → **立刻回滚**，别硬撑。

## R6. 高危操作不外包

- 可以外包：**只读排查、写代码、写文档、跑单测**
- **不可以外包**：换 DLL、重启客户端、改数据库、部署上线
- 为什么：子代理看不到全貌、不会权衡风险，且它的"成功"往往只是它的自测通过。

## R7. 任何「修复」上线前必须有可回滚点

- DLL：备份到 `archive/`
- 数据库：`db_storage` 整体复制一份（含 `-wal` / `-shm` / `.material`）
- 配置：改之前 `cp` 一份
- 没有回滚点 → **不许动手**。

## R8. 不能用「单次测试通过」宣布修好

- 这类 bug（静默失聪、间歇性）**必须**用「连续 N 分钟零失败 + 实测收发」来判定。
- 推荐判据：
  - `bridge-hook.out.log` 里 `轮询失败` **增量 = 0**，持续 ≥30 分钟
  - 期间每 5 分钟实测一次收发（`SendTextMsg` → `/api/status` 的 `msgsIn` 增长）
- 端口不通/客户端正在重启**不算**失败，别混进判据。

## R9. 文档与代码不一致时，以代码为准，并补文档

- 已知 9 条不一致记录在 `docs/AI-一键部署.md` §10。
- 改代码时顺手看那条对应的文档要不要改。

```
✓ 自动拉起客户端 = 关闭（grep WECHAT_AUTOLAUNCH）
✓ 看门狗在（bridge 日志里 5 分钟一次的健康检查，健康时静默）

✓ 备份齐全（DLL GOOD / db_storage / memory）

```

## R11. 功能没确定之前，**不推送 GitHub**

判定「确定」的标准（三条全满足才算）：
1. 用户明确说「可以 / 就这样 / 没问题」；
2. 至少一次**真实场景**验证（不是单次测试通过——见 R8）；
3. 没有留下未收尾的临时改动（临时脚本、调试开关、被弃用的配置值）。

在那之前：
- 改动只留在本地工作区，**可以 commit 到本地仓库，但不要 push**；
- 被否掉的方案，**不要为了「留个记录」推上去**——要留就在本地留；
  已经推上去但后来弃用的，必须补一条明确标注「已弃用」的提交说明原因（见 R9）。

为什么定这条：
2026-10-21 那天本地生图方案改了 5 轮（img2img / inpaint / IPAdapter / 合成融合 / LoRA），
每一轮都当作「对了」推了上去，最后全部弃用 —— 仓库里堆了一串没人要的历史，
而且文档一度和实际配置互相矛盾（代码默认 comfy、配置是 agnes）。

## 附：微信数据库的几个坑（别再重新踩）

| 坑 | 表现 | 正解 |
|---|---|---|
| **消息库分片** | 写死 `message_0.db`，微信换到 `message_1.db` 后**永久失聪** | 自动发现：试 `message_0..3`，用第一个有 `Msg_` 表的（桥已实现，缓存 30s）|
| **懒加载** | `dbs=0`、`get database handle failed` | 让用户在微信里**点开聊天/通讯录**，库才会挂载 |
| **`contact.db` 会被反复卸载** | 映射表空 → 群消息被当**私聊**回复 | 映射持久化到 `data/table-map.json`（桥已实现）+ `session.db` 兜底 |
| **`IsLogin` 是上游坏标志** | 永远 0 | 用 `hWeixin` 判断，或直接看能不能读库 |
| **`.factory` 隔离** | 聊天记录消失、库被移走 | 备份 → 还原全部 6 个文件（`.db`/`-wal`/`-shm`/3 个 `.material`）→ 等它加载 |


## R12. 重启微信后，登录窗口**按回车**进入，不要用 UIA 点击

> 用户 2026-10-21 15:42 明确指示：「重启微信不需要你去点击进入微信，直接回车键就可以了」

- `mmui::LoginWindow` 上按 **ENTER** 就能进入（纯键盘动作，无坐标依赖）
- 为什么不用点击：UIA 的 `Invoke` 对 Qt 窗口**无效**；「UIA 取坐标 + 鼠标点击」实测会**失手**（15:39 连点两次无反应，窗口前台/坐标都会漂）
- `scripts/safe-restart-client.ps1` 第 4.5 步已改为：置前台 → 发 `{ENTER}` → 验证（进程数变多 且 LoginWindow 消失）；**失败才**回落到 `click-enter-wechat.ps1`
- 手动同理：看到登录窗口，直接敲一下回车

## R13. 重启客户端是**不可中断**的完整流程

> 2026-10-21 15:21 的教训：安全重启脚本跑到一半被打断（已关客户端、未走完启动与进入），
> 客户端进入半初始化状态 → 收发全断；再叠加手动 `WM_CLOSE`（微信只最小化到托盘），
> 最终用户从托盘退出时带着未落盘数据 → 微信报「数据库损坏」。

- 跑 `safe-restart-client.ps1` **必须一次跑完**，中途不许 kill 它的 job
- 如果已经被打断：**不要再叠操作**，直接从头完整跑一遍
- 微信弹「数据库损坏」→ 点它自己的「**开始修复**」（`mmui::SupportStorageCommonWindow` 窗口），比手改数据库安全
- 修复后会重启客户端，此时 hook 可能挂错地址（`registry.count=0`、拿不到库名）→ **再完整重启一次客户端**即可恢复

## R14. 任何「额外下载类」hook 必须限流 + 只对新消息生效

> 2026-10-21 17:07 的教训：CDN 重放功能没有限流、不区分新旧消息，
> 微信登录后重新拉取一批历史图片时，每张都额外触发 2 次 CDN 下载，
> 短时间内积累大量额外任务 → **客户端崩溃**（当天 3 次 dump，17:07 后进入安全模式）。

**硬性要求（下次再做这类功能时必须满足，否则不许启用）：**

1. **只对新消息生效**：消息时间与当前时间相差 > 60 秒的一律跳过
   （登录/刷新会重下历史图，这类必须放过）
2. **每张图只下一次**，不要「两种参数各下一次」
3. **全局限流**：任意 2 秒内最多 1 次额外下载；连续 10 次后强制休息
4. **独立开关 + 默认关**，且出问题能**不重启客户端**就失效（文件开关）
5. **上线前先观察 30 分钟**：盯着 `crashinfo\reports` 有没有新 dump；有就立刻关

**当前状态**：该功能已停用（`version.dll` 已回滚成原版 A1EE8E22），
带探针的版本另存在 `D:\dsh-private\version.dll.with-probe-418278E5`。

## R15. 高分辨率图 provider 的安全实现要点（已落地）

> 2026-10-21 17:11 起使用「安全版」，实测：装后 1 小时无新增崩溃，单条消息只触发 1 次下载。

参数（DLL 内硬编码，改需重新编）：

| 保护 | 参数 | 说明 |
|---|---|---|
| 老消息过滤 | 60 秒 | 消息时间与当前差 > 60s 直接跳过（登录重下历史图不会触发） |
| 下载次数 | 1 次/图 | 客户端已在取原图档时完全跳过 |
| 全局限流 | 2 秒 1 次 | 高频收图也不会堆积 |
| 突发冷却 | 60 秒 10 次 → 休 60 秒 | 防瞬间风暴 |
| 同名去重 | 60 秒 | 同一条消息只补一次 |

**总开关**：`hook-vuprobe.on`（安装 hook，删了功能完全不生效）+ `hook-cdn-replay.on`（启用下载）。

**上线检查表**：
1. 装前 `crashinfo\reports` 今天 dump 数记为基线
2. 装后观察 30 分钟，dump 数不增加
3. 发一张新图，日志应只有 **1 条** `replay ok`
4. 老消息重下时应看到 `replay skip(old Ns)` 而不是真的下载

### R15 补充：视频能力（2026-10-21 验证通过）

**产品行为（可公开）**：
- 机器人能拿到视频的**完整内容**（不只是封面），不需要人工点开播放
- 画面：按视频时长**每秒 1 帧**（上限 60 帧），每 **20 帧一张联系表**（长视频自动分成多张）
- 声音：全程音轨转文字，台词交给模型理解
- 多张联系表逐张识别，按「【第 N/M 段】…」拼接成完整描述
- 读完自动删除临时文件（抽帧表、音轨、视频副本），不占磁盘

**实测证据**：
```
视频内容已抽取：4 帧（每秒 1 帧）→ 1 张联系表｜时长 3.8s｜音轨 3.84s
已删除临时音轨 WAV
已删除视频原文件（videoDeleteAfterRead）
```

**教训（必读）**：判断"文件是否下完"**不能只看大小阈值**。
曾经因为文件还在写就复制，拿到半截视频 → 抽帧/时长/音轨全对不上 →
机器人描述了错误的视频内容。正确做法：连续两次采样大小一致 + 与消息声明的字节数比对。

## R16. 收藏群友表情：必须校验文件头 + 识图回写标签

> 2026-10-21 实装「收藏别人表情包并发送」时踩到的四个坑，按顺序都踩了一遍。

1. **收藏要挂在「取媒体」这个必经点上**，不能只挂消息回调 ——
   消息可能来自数据库轮询，根本不经过回调（第一次收藏失败就是这个原因）。
2. **表情候选地址里混着加密封装**，而且它往往比原图还大；
   若按「取最大」逻辑选，就会把加密垃圾存进库（表现为：文件头随机、识图报 Unsupported）。
   → 必须**校验文件头**（JPEG/PNG/GIF/WEBP）再收。
3. **GIF 动图不能直接识图**（模型链路只吃静态图）→ 先抽首帧转 PNG 再识别，
   GIF 本体留给表情库（发送时仍用它）。
4. **收藏完必须回写标签**：没有标签的表情按语境永远匹配不到，等于白存。
   把视觉模型对表情的描述写回库（一次 IPC）。

**附带教训（数据库）**：客户端重启后 hook 的库句柄可能「半坏」——
`SELECT 1` 能回、查任何表都回空。恢复只能重启客户端。
因此**分片探测绝不能盲试不存在的库名**（盲试会让 hook 缓存坏句柄，整库失聪）。
